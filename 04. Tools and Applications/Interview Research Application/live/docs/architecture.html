Panel synthesis · live prototype

What we built, and what talks to what

The submitted site was a finished page with nothing running behind it. This is the system that produces that kind of page on transcripts nobody has read — and the thing worth understanding is not the boxes, it's which parts are allowed to be wrong.

Three kinds of work

Every step in this system is one of three things, and the difference is the whole design. A model can be wrong and needs checking. Arithmetic cannot. A person's judgment is the thing that decides what the machine is allowed to argue.

Deterministic— arithmetic and string matching. Same input, same answer, every time.
Model— Claude. Can be wrong, so it never gets the last word.
Human— you, confirming or rejecting each fact.

The request path

Three participants. The one fact that makes a back end necessary is where the API key lives: it sits in the server's environment and never travels to the browser, so a stranger can run extraction without ever holding your credentials.

The trust chain

This is the part that matters. The model is allowed to be wrong twice, and both times something catches it before its output can travel: a deterministic check on the quote, then your judgment on the reading. Everything downstream sees only what survived both.

Why the gate is drawn full width

Nothing gets past it. The browser sends only confirmed atoms to the drafting and grading endpoints, and the server independently re-checks every cited id against that same set. Reject an atom and it is absent from the request, not filtered out of the answer.

How a panel is held

Each interview is extracted on its own, but the atoms land in one pool with the expert stamped into the id. That prefix is what lets a rollup show three scores in one cell, and what lets the drafting step tell "all three said this" from "one said this."

What actually changed

Both the submitted site and this one were produced the same way — Claude drafts, a human approves, the result gets published. The difference is that in the submission that loop ran once, offline, and got frozen into a file.

The files

FileRunsDoes
api/extract.pyserver Passcode gate, file decode, routes the three endpoints, error handling. Never lets a secret into a response.
api/_pipeline.pyserver The schema, the prompts, the quote check, and the two drafting tools. The contract lives here.
public/index.htmlbrowser Every screen, all state, all rollup arithmetic. One file, no build step.
dev/check_schema.pyguard Fails if the live schema drifts from the scored one, which would quietly invalidate the 52/52 figure.
dev/local_run.pyguard Runs the real server code path locally, so a deploy fails only on environment, never on logic.

What it would still need

The one that decides whether this is a product

The schema is hardcoded to ITSM. The vendor list is a literal — ServiceNow, BMC, Freshservice, Ivanti, Jira, Zendesk, ManageEngine — so a panel about surgical robotics extracts nothing. Generating the schema per workstream from that project's interview guide, confirmed once by a human, is the feature that turns a working demo into something Synquery could run across hundreds of studies.

The shape already generalizes: criteria, ratings, pricing, terms, loyalty, switching is a reasonable spine for any buying-decision study. It is the vocabulary that has to become per-project.

A database

State lives in one browser tab. Nothing is shared, nothing survives a cleared cache, nothing reaches a colleague.

Accounts and projects

One shared passcode and one panel at a time. No notion of who approved what, or of a client engagement.

An audit trail

Confirmations are anonymous browser state. In regulated research you have to be able to show who signed off on a number.

Snapshots

A deck cites a panel that keeps changing underneath it. Findings need a version they were true at.

Export

You can synthesize a panel and still not get the deliverable out of the page.

Cost and scale limits

Nothing stops one user burning the key, and a very long transcript would need chunking rather than one context window.

Roughly: the database, accounts, projects and export are a week of unglamorous plumbing. The schema generator is the interesting problem, and the one that decides whether this is a tool for one study or a product for a business.
